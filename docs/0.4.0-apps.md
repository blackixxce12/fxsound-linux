# FxSound for Linux 0.4.0 — per-application presets

The user asked for this before 0.4.0: every application that plays or records can have its
own preset, per direction, remembered in a local store. Example: Battlefield 6 → *Gaming* on
the output, Brave → *Volume Boost* on the output, Discord → *Headset* on the input — all at
the same time.

## How it works on PipeWire

One chain cannot run two presets at once, so an application with a preset of its own gets a
**route**: an extra pair of FxSound nodes with that preset's chain, attached to the same real
device as its lane. The application's stream is moved onto the route by writing the
standard per-stream target into the `default` metadata — subject = the stream's node id,
key `target.object`, type `Spa:Id`, value = the route node's `object.serial` — exactly what
pavucontrol's "move stream" does. WirePlumber 0.5.17 honours it
(`/usr/share/wireplumber/scripts/linking/find-defined-target.lua`, rescans on the change,
`linking.allow-moving-streams` must be true — it is by default). Deleting the key moves the
stream back. Streams marked `node.dont-move = true`, streams with an explicit
`target.object` property pointing somewhere else than FxSound, FxSound's own nodes and the
echo canceller's nodes are never touched.

- Output: route pair = `fxsound_route_o<N>` (Audio/Sink, description
  `FxSound (Output) · <preset>`) + `fxsound_route_o<N>_play` (playback stream to the output
  lane's target), node.link-group `fxsound-route-o<N>`, passive like the main output pair.
- Input: route pair = `fxsound_route_i<N>_capture` (capture stream from the input lane's target
  — or from `fxsound_aec_source` while echo cancellation runs) + `fxsound_route_i<N>`
  (Audio/Source, `FxSound (Input) · <preset>`), link-group `fxsound-route-i<N>`; the recorder's
  capture stream is moved onto that source.
- Each route has its own DSP (a `LaneDsp` built on the main loop), its own ring, its own
  params triple buffer whose writer the **engine** owns (params arrive over the control
  channel, never on the RT path). Routes never claim a session default.
- At most `MAX_ROUTES_PER_LANE = 4` distinct presets per lane at a time; an application whose
  route cannot be created stays on the lane and the window says why (a `Warning`).
- A route with no streams for 10 s is torn down. Routes follow their lane: lane retargeted →
  route pairs rebuilt on the new device; lane detached → streams moved back (metadata keys
  deleted) and routes torn down; engine exit → keys deleted before nodes go (the exit
  hand-back already confirms metadata writes with a sync — reuse it).
- Route node names match `fxsound_route_*` and join the "our nodes" filter so they never appear
  as devices.

As built (`crates/fxsound-audio/src/app_routes.rs` plans, `engine/route_pairs.rs` carries the plan
out): the app sends every rule whose preset its lane's store has and loads, under the rule's own
key, whether the application runs or not, and resends only when a rule, a preset or a level
changes — never because a stream came or went (`crates/fxsound-app/src/app/per_app.rs`). Beside
them it sends, with an empty preset, every rule that follows the lane (by choice, or because its
preset is gone or does not load) and could outrank one of them for some stream
(`AppKey::may_outrank`): a Flatpak Firefox whose own rule follows beside the native Firefox's rule
on a preset, which matches it by its program. The engine takes an empty preset as "follow" and
picks each stream's entry with `AppKey::best_match`, in the order sent (the store's, lane by
lane), so it runs for every stream exactly what the store's own lookup says — a property test
checks it over every overlap of flatpak ids, programs and names. A route is built only when a
running stream of its lane has such a rule naming its preset, and is kept for 10 s after its last
stream leaves (`ROUTE_IDLE`), so a player that closes its stream between two tracks comes back to
the same pair, and a new stream is moved at once, with no round trip through the app; one whose
preset no rule names any more goes at once. A new route takes the lowest number free in its lane and keeps it for its life; a preset
that would need a fifth takes the place of the route unused longest, and with none unused its
streams stay on the lane and the window is told once per application
(`TOO_MANY_APPLICATION_PRESETS`, which the app translates). A route's two nodes carry the lane
pair's own properties with the route's names, descriptions and link-group, and
`priority.session = -1`, below anything WirePlumber could fall
back to. It plays at its lane's volume and is silenced with its lane while the system sleeps: its
chain reads the lane's volume, and its own node's adapter keeps a mixer's volume at unity, as the
lane's does. On waking its chain's history — filters, leveller, denoiser — is cleared with the
lane's, through a reset queue of its own. On a server before 0.3.68 its stream on the device is not
passive and not paced; it holds the device for as long as the route lives. A later
`SetAppRoutes`' parameters are written into a running route's buffer, and a new voice chain is
handed over as the input lane's is. Routes follow
their lane's pair — device, node serial, format, the echo canceller's source — are kept while the
lane is between pairs, and go with a lane switched off, their streams' keys deleted first.

The key is written with type `Spa:Id` and the serial of `fxsound_route_o<N>` or
`fxsound_route_i<N>`. Measured on PipeWire 1.6.8 with `pw-metadata`: the server clears a subject's
keys when the subject goes, and keeps none for a subject that does not exist. A key someone else
wrote that names anything but a route node of FxSound's — a mixer moving the stream to other
speakers — marks the stream as moved by hand: FxSound neither moves it again nor deletes the key. A
key that puts a stream onto a route node of this process's, there or gone, is FxSound's whoever
wrote it, and is put right by the rules: kept (and taken as written, with nothing sent) where it
names the route the stream's rule wants, rewritten where it names another, deleted where the stream
has no rule. WirePlumber 0.5.17 saves every target written for an application by the target's
`node.name` and writes it back each time the application opens a stream (`node/state-stream.lua`,
`node.stream.restore-target`, on by default); nothing clears the saved name once the application
has quit while routed, and route numbers are taken again by other presets, so such a key names
whatever preset runs under that number now and cannot be told from a mixer's. A delete someone else
sent, or a key written over FxSound's, takes FxSound's write back (unless a write of FxSound's is
still on its way, which the server applies after it), and the next tick writes the key again where
the rule still wants it; the server reports each change once, in order, and none that changes
nothing (measured on 1.6.8 with `pw-metadata -m`). A key never names a node that is about to go: in
one tick the deletes and the writes onto routes that stay are sent before any route is taken down,
and a stream whose route is rebuilt — on the lane's new device, after a failure, or under the same
number for another preset — has its key deleted first and written again once the new node is
announced; while its lane is between pairs a route keeps its node and its streams their keys. A
killed FxSound's keys name serials the next run never made, and are left as they are until their
streams go; WirePlumber falls back for them in the meantime. On exit every key that puts a stream
onto a route node of this process's is deleted, whoever wrote it, with the hand-back of the
defaults and confirmed by the same `sync`, before any node goes.

A recorder's key naming a playback route's sink (`fxsound_route_o<N>`) puts it onto no route:
WirePlumber links a recorder to a sink's monitor (`lutils.canLink`), so it records what the route
plays and nothing goes through the route's chain. It is what `pipewire-pulse` writes when the user
points a screen recorder at `Monitor of FxSound (Output) · <preset>`, and FxSound never writes it
(a recorder is only planned onto the input lane's routes). So it is the user's, like a key naming
any other node: the recorder counts as moved by hand, and the key is never deleted nor rewritten,
not even on exit. Which streams are recorders the engine knows from their `media.class` when they
appear.

A stream FxSound does not move can still sit on a route: one whose own properties name the route's
node (by name, serial or id) and which has no key in the metadata, one saying `node.dont-reconnect`
that WirePlumber restored onto a route (FxSound deletes that key — it moves nothing, and is what
WirePlumber would restore next time — and remembers the route for as long as the stream lives), or
a recorder whose key names a playback route's sink, whose monitor it records. Such a stream keeps
its route in use: it is never idle, never gives its place to another preset, and a route whose rule
goes is kept (logged once) until the stream has left, then goes at once. The private graphs the
tests run in have no WirePlumber, so the tests read back the pairs and the keys, and write keys the
way WirePlumber's restore does, but cannot watch a stream move.

## Identifying an application

`AppKey { binary, name, flatpak }` from the stream node's properties:
`application.process.binary` (Wine/Proton set the `.exe` name), `application.name`,
`pipewire.access.portal.app_id` (Flatpak). Matching order: flatpak id, then binary
(case-insensitive, basename), then name. The display name is `application.name`, else the
binary. The key survives restarts of the application.

As built (`crates/fxsound-audio/src/app_streams.rs`): a stream node's registry global carries
only `application.name` of these; the rest, and `target.object`, `node.dont-move` and
`stream.capture.sink`, are in the node's info (measured on PipeWire 1.6.8 with `pw-cat`). A
native stream that sets nothing carries `application.name` alone, and its binary is its client's
property. So the engine binds every application stream and every client: binary and name come
from the stream, else from its client; the Flatpak id from the client first
(`pipewire.access.portal.app_id`, else `pipewire.sec.app-id` when `pipewire.sec.engine =
org.flatpak`; the access control sets them there, and a stream can claim any id in its own
properties), and only when the client has none from the stream, read the same way. A client that
carries only `pipewire.sec.app-id` therefore beats a stream's `pipewire.access.portal.app_id`.
Application streams are nodes of media class exactly `Stream/Output/Audio` or
`Stream/Input/Audio` that are not FxSound's own (`fxsound_*` lane nodes, `fxsound_route_*`,
`fxsound_aec_*`). A recorder of what a sink plays is listed only when it records FxSound, and is
then never moved: behind a microphone's route it would record the microphone. It is one either
by `stream.capture.sink = true` — and records FxSound when it names an FxSound node as its
target, or names none while FxSound's sink is the default sink — or, with no flag at all, by
naming a node of FxSound's output lane that WirePlumber 0.5 links a recorder to
(`linking/find-defined-target.lua`, `lutils.canLink`): `fxsound_sink` or `fxsound_route_o<N>`
by `object.serial` or node id (a number is looked up with no direction check, and a recorder may
link to a sink's monitor), or `fxsound_output` or `fxsound_route_o<N>_play` by name or number.
`pw-record --target <serial of fxsound_sink>` records FxSound. A recorder that names the input
lane's nodes records a microphone and may be moved. A stream with no identifier at all (no
binary, name or Flatpak id, its own or its client's) is not listed, and neither is one whose
info or whose client's info has not arrived yet. A `node.dont-move` stream and a stream whose
own target names another node are listed but never moved, and so are a `node.dont-reconnect`
stream (what `pipewire-pulse` makes of `PA_STREAM_DONT_MOVE`: WirePlumber never moves it once
linked, and never links it again once its target goes) and a `node.dont-fallback` stream
(WirePlumber destroys it when the target its metadata names is not there). `AudioToUi::AppStreams` goes out on
the supervisor tick, whole, only when it changed.

## Core API (`fxsound-core`)

```rust
pub struct AppKey { pub binary: String, pub name: String, pub flatpak: String }   // serde, Eq, Hash; fn matches(&self, other) per the order above; fn display(&self) -> &str
pub struct AppStream { pub id: u32, pub direction: DeviceDirection, pub app: AppKey, pub route: Option<String> /* preset name when routed */ }
pub enum RouteParams { Output(DspParams), Input(InputDspParams) }          // Copy payloads
pub struct AppRoute { pub direction: DeviceDirection, pub app: AppKey, pub preset: String, pub params: RouteParams, pub chain: String /* input chain spec name */ }
UiToAudio::SetAppRoutes(Vec<AppRoute>)        // the full set; the engine diffs it
AudioToUi::AppStreams(Vec<AppStream>)         // every non-FxSound client stream of both directions, sent on change
// settings: nothing — the store is its own file (below)
```

The app resolves presets to params (it owns the preset stores) and resends `SetAppRoutes`
whenever a rule changes, a preset used by a rule is saved/renamed/deleted, or the global
output levels (master gain, balance, leveling, band count) change.

## The local store

`~/.config/fxsound/apps.toml` (`$XDG_CONFIG_HOME`), written atomically like settings.toml:

```toml
[[app]]
binary = "bf6.exe"
name = "Battlefield 6"
flatpak = ""
output_preset = "Gaming"      # absent = follow FxSound's output preset
input_preset = ""             # absent/empty = follow
last_seen = 1790000000
```

A module `fxsound_core::apps` (or `fxsound-preset::apps`) with load/save/upsert/forget,
per-file-tolerant loading (a bad file is moved aside to `apps.toml.bad`, or `apps.toml.2.bad` and
so on, never silently lost), and a cap of 500 remembered applications (oldest `last_seen`
forgotten first, among the rules that only follow the lanes before any with a preset of their own).
A rule whose preset no longer exists falls back to "follow" and the window says so once.

## Interface

- **Settings ▸ Applications** (a fifth tab, nav row at (20,290,150,40), an icon in the nav
  icons' style): a scrolling list of applications — running ones first (a small dot), then
  remembered ones — each row the display name and, for the lane(s) it uses, a preset combo
  whose first entry is "FxSound's preset" (follow). A row can be forgotten (the ✕ the device
  priority list already uses). Same fonts, geometry style and widgets as the device list.
- The Pro window's preset combo tooltip, when the edit direction's lane has routed
  applications, lists them ("Battlefield 6 → Gaming"). Nothing else in the main window.
- CLI: `--app-preset APP=PRESET` (output), `--app-input-preset APP=PRESET`, `PRESET` may be
  `default`; `--list-apps [--json]`. D-Bus: `SetAppPreset(s app, s direction, s preset)`,
  `ListApps() -> s` (JSON), signal `AppRouted(s app, s direction, s preset)`. `--watch`
  event `app_routed`. `--status --json` gains `apps[]`.
- Every string translated (28 port tables + bg).

As built (the command line and the bus, `crates/fxsound-app/src/cli.rs`, `commands.rs`,
`dbus.rs`, `app/per_app.rs`; `packaging/fxsound.1` documents it):

- `APP=PRESET` splits at the first `=`; both halves are trimmed. `PRESET` is `default`,
  `follow` (any case) or empty to follow the lane, else a preset's exact name in that lane's
  list; a name only the other lane has is refused with a pointer to the other option. Both
  options may repeat; they run right after `--preset` on a line (so `--save_preset X
  --app-preset game=X` works) and neither raises the window.
- `APP` names applications as `apps_named` finds them: the store first — by Flatpak id, else
  program (last path component), else name, each case-insensitively; the first of the three
  any rule answers to decides, and **every** rule that answers is changed (a native and a
  Flatpak Firefox both, for `firefox`). When no rule answers, the streams playing now are asked
  the same way, so a running Flatpak the native rule covers is still reached by its id (it gets
  a rule of its own). When nothing answers, the preset is kept for `APP` as the identifier it
  looks like (`unseen_key`): a path or a `.exe` is a program, three or more dot-separated parts
  that each start with a letter or `_` (`com.discordapp.Discord`) a Flatpak id, text with a
  space (`Battlefield 6`) a name, one word a program — each identifier is compared with the same
  one of a stream only, so a Flatpak id kept as a program would never match. A note on stderr
  says what it was kept as (exit 0); following the lane for such a name adds nothing (also a
  note).
- Cold start: `--app-preset` / `--app-input-preset` are honoured once the preset lists are read,
  like `--preset`, and FxSound starts. A name the store does not answer to is held (a note says
  so) until the engine's first report of the streams, or 3 s (`STREAMS_PATIENCE`: nothing is
  reported while nothing plays), or exit, and then chosen as a running FxSound would choose it —
  so a game started before FxSound is reached through its own stream; the log says what became of
  it. `--list-apps` with no instance answers from `apps.toml`
  read-only (a file that does not load is reported and left in place, not moved aside), nothing
  running, and starts nothing.
- `--list-apps` prints one `key=value` line per application in the Settings pane's order
  (`name binary flatpak running output_preset input_preset routed.output routed.input`, the
  `--watch` plain spelling); `--json` and D-Bus `ListApps` print `{"schema":2,"apps":[…]}`.
  `--status --json`'s `apps[]` holds the same objects: `name` (the display name), `binary`,
  `flatpak`, `running`, `output_preset` / `input_preset` (`null` = follow, as written in the
  store), `routed: {output, input}` (the preset of the route the engine reports the streams on,
  `null` on the lane).
- Settings ▸ Applications: a row heard this session has a combo for each lane it was heard on
  and each lane it has a preset of its own on; a row not heard this session has both, since the
  store does not record the lanes an application uses and a preset on one lane says nothing about
  the other.
- `apps.toml` is written at once for a choice, a forgotten row and a new application, 5 minutes
  after one seen again, and at exit; a write that fails is retried every 30 s and at exit.
- D-Bus `SetAppPreset` takes the direction as `SetEditDirection` does and `""` as follow;
  `AppRouted` names the application by its display name and carries `""` for "back on the lane".
