# What changed in the output DSP after `0f05ba5` — the inventory for "Interface and sound"

The level "Interface and sound" of «Like FxSound for Windows» (`docs/0.5.0-windows-parity.md`)
brings back the Windows DSP of the output lane: at steady state the lane must render as the engine
before the 0.4.0 audit's fixes did, bit for bit or below −120 dB. Before any of it is built (W1b–W1d),
this inventory lists **every change to the sound of the output lane since `0f05ba5`**, the last
commit before the fixes, and classifies each one:

- **S** — an item of the 0.4.0 audit (the phase F list) that the approved table sends to "Interface
  and sound": its `0f05ba5` behaviour comes back at that level, as the `legacy` path of its stage.
- **never** — kept at every level: a transition fix (clicks, thumps, glides: TRANS), a port error
  where Windows is wrong (PORT), or data safety (DATA). The contract's §2 names them.
- **I** — changes only what the window shows or how it is operated; handled by "Interface".
- **input** — the microphone chain only; no level touches it.
- **none** — no sound: a refactor, an interface of the engine, dead code, documentation.

**Nothing falls outside these classes**, so nothing stops the phase for a question to the user.
Five findings change how W1b–W1d are built; they are at the end ("For W1b–W1d").

How it was made: `git log 0f05ba5..HEAD -- crates/fxsound-dsp/src` gives the nine commits
(`192dbbd`, `4a3187a`, `c4c40fa`, `125c64e`, `5cb4670`, `3fedcc3`, `a512f33`, `f2a507f`,
`baebc0b`). The net non-test diff `0f05ba5..HEAD` of `crates/fxsound-dsp/src`,
`crates/fxsound-core/src/{lib.rs,messages.rs}`, `crates/fxsound-audio/src/lane_dsp.rs` and
`crates/fxsound-preset/src/lib.rs` was read unit by unit (function, type or constant), with the
audit references the new code carries; the application's reading of a preset (`music_controls`)
was compared with the one at `3596e99`. Test modules are left out: they change no sound. The
output DSP has not changed since `v0.4.0` (`git diff v0.4.0 HEAD -- crates/fxsound-dsp/src` is
empty), so this is also the difference between 0.4.0 and the Windows engine.

## The reference commit: `3596e99`, not `0f05ba5` itself

`0f05ba5` is the last engine before the fixes, but its application is older than the band-count
work of the 0.4.0 controller (`a021859`, "Band counts … behave like upstream"): it put a preset's
**own** bands in the window whatever band count the user had chosen, which neither Windows nor any
release did. The Windows reading — the user's band count kept, a preset of another count remapped
onto it **by position** (`DfxDspEq.cpp:127-247`) — is `3596e99`'s, the last commit of the
controller branch before it took the audit's fixes in (`d9138b1`). `3596e99` has `0f05ba5`'s engine
byte for byte:

```text
git diff --stat 0f05ba5 3596e99 -- crates/fxsound-dsp crates/fxsound-core/src/lib.rs \
    crates/fxsound-core/src/messages.rs crates/fxsound-preset/src/lib.rs \
    crates/fxsound-audio/src/lane_dsp.rs          # empty
```

So A1 holds the working tree to `3596e99` (`scripts/windows-parity-bitexact.sh 3596e99`). The
roadmap names `0f05ba5`; its application could not answer the question at 20 and 31 bands.
`scripts/reference-checkout.sh 0f05ba5 …` still works: it reads a preset on the preset's own band
count there, as that application did.

## For W1b–W1d

1. **The gain stage moved.** `3fedcc3` runs the master gain and the balance before the equalizer;
   `0f05ba5` ran them between the equalizer and the leveller, and with the power off applied the
   master gain alone, only while the equalizer was on. The engine's documentation says the two
   orders "give the same signal" — they do in exact arithmetic, not in `f32`: an IIR cascade fed
   `g·x` does not round like `g` times the cascade's output. So R3's `legacy` path puts the stage
   back where it was, or A1 fails on every case with a master gain or a balance (the harness's
   "gain" level set exists for this).
2. **Dynamic Boost's limiter is `input/limiter.rs`.** The voice chain's limiter is the same code.
   #8, R1 and R2 come back for the output lane only; the voice chain keeps the fixed limiter at
   every level.
3. **The reference is `3596e99`** (above), and for #39 and #44 the Windows C code (A2), not the
   port's `0f05ba5`.
4. **The transitions stay**: cold-start renders of the working tree already match `3596e99` where
   no S item is involved (see the baseline), so #9–#11 and the E6a dip do not stand in A1's way.
5. **A1 has a second pass, and W1d closes it.** The harness's switching pass (`switching`) plays
   each case's preset, then picks the next shipped preset at a quarter of the material, changes
   the band count (10 → 20 → 31 → 10, the preset read again on the new ladder, then
   `ResetFilterState`) at half and moves one effect's slider at three quarters, and compares
   everything but the `GLIDE_SECONDS` (20 ms) after each switch. Against `v0.4.0` it is identical
   and holds A3 in CI with the cold pass. Against `3596e99` it cannot pass before the cold pass
   does — every switched case goes through 20 or 31 bands, where the snapshots differ until W1c
   — so W1b and W1c run it with `--report` (W1b gates the cold pass's ten bands, below), and
   **W1d**, which builds the live switch between the paths, makes it pass: the `legacy` paths
   must settle into `3596e99`'s steady state within the glide after a change as well as from a
   cold start. The report's `past_limit_ms` says how long
   a difference past −120 dBFS outlasts each switch; if the filters' own tails need longer than the
   glide, W1d says so and sets `FXSOUND_BITEXACT_SETTLE_MS` in the job with the measured value,
   rather than widening the limit. `3596e99`'s application also cleared the filters on every
   preset picked and remapped the curve on screen when the band count changed; the harness plays
   the working tree's events on both sides (the transitions stay, item 4; the band count's
   reading of a curve is #13, #45, W1c).

## W1b: Volume Leveling, Dynamic Boost and its limiter

`DspParams::compat` (`fxsound_core::DspCompat`: `Linux` or `Windows`) says whose DSP the music
chain plays. The application sends `Windows` from «Like FxSound for Windows» = Interface and sound
on, to the output lane and the applications' output routes alike (`MusicLevels::of`,
`App::sync_params_from_state`); the voice chain has no such field. W1b gives it to the first two
stages:

- **Volume Leveling** (`leveller.rs`, `leveller_legacy.rs`): #1–#4 taken back — the peak safety on
  the 120 Hz side chain's peak, one step per call, the subwoofer neither analysed nor levelled, both
  ends of a call's ramp clamped to the peak-safe gain. The statistics, the decision and the quiet
  state machine are the port's own functions, which the audit did not change; the let-down when the
  stage is switched off (#11), the stage left out while its owner is off, the subnormal flush (#5)
  and the guard against a non-finite statistic are the same at every level.
- **Dynamic Boost** (`effects/dynamic_boost.rs`): #6 and #7 taken back — the flat 1.06 floor and
  the left channel's level. The static boost's glide (#11) stays.
- **Its limiter** (`input/limiter.rs`): #8, R1 and R2 taken back for Dynamic Boost only — no
  channel linked, no hold, and the attack left to overshoot (`LookaheadLimiter::set_overshoot`).
  The voice chain's limiter keeps all three.

Each stage switches without allocating and carries on from the gain it is playing (the leveller's
ramp, the limiter's loudest envelope), and the back-off's floor, the one part that would step the
gain at once, glides over 20 ms: switched at once under a 50 Hz tone at −6 dBFS at slider 0 it
clicked at −35.6 dBFS above 1 kHz. Under steady tones that drive the back-off, the limiter and
the leveller, a switch each way now leaves −92.2 dBFS above 1 kHz at worst
(`switching_to_the_windows_dsp_and_back_under_a_steady_tone_does_not_click`). The crossfade
between whole paths, A4 and a scenario of the graph's click test are W1d's. The unit tests hold
the three stages at `Windows` to the port's code of `0f05ba5`, taken with `git show`, bit for bit
on 1, 2, 6 and 8 channels, the subwoofer on channel 3 (`OriginalLeveller`, `OriginalLimiter`,
`OriginalBoost`; the leveller in ragged calls, a quiet passage then a burst), and give the audit
tests of #1–#4, #6, #7, #8 and R2 a twin each that pins the Windows behaviour. The application's
tests see `compat` reach both the output lane and every application's output route, and leave a
voice route's snapshot alone.

## W1c: the equalizer, Ambience, the gain stage and the reading of a preset

The rest of the output lane's S items, and the application's reading of a preset at Interface and
sound. Each is `0f05ba5`'s arithmetic, or for #39 and #44 the Windows C code's, inside the port's
transitions, as in W1b:

- **The equalizer below 20 Hz (#12).** `biquad::calc_parametric_in`: the Q cap goes on down the
  original's line, negative under 17.9 Hz, so a band there is the flat gain the Windows build
  plays. `GraphicEq::set_compat` redesigns the bands below 20 Hz only, crossfading as a moved band
  does.
- **The gain stage (R3, #44).** `Engine`: between the equalizer and the leveller inside the
  GraphicEq block, as `0f05ba5` ran it (finding 1 above), so the equalizer's switch takes the
  master gain and the balance with the block again (faded, #11); with the power off the master
  gain alone on every channel, and only while the equalizer is on (`sosProcessBuffer_MasterGainOnly`);
  the balance on channels 0 and 1 of a stereo stream and nowhere else — the Windows surround path
  multiplies every channel by the master gain alone (`SosProcess.cpp:846-908`), which `0f05ba5`
  got wrong by balancing channels 0 and 1 of any layout. The Windows build has no path for 3, 4, 5
  or 7 channels; they take the master gain alone. The glides and the power dip stay.
- **Ambience (#39), the stage and the slider together.** `Ambience::set_compat`: the bypass test
  on the stored value, as before, and the wet/dry pair the Windows C code computes for every
  stored value, the warp run off the end of its range for 13 to 38 included (a tail in opposite
  phase at 13, none at 38), with the C's own `double` constants. `scale::slider_to_value_in`: the
  slider's straight line, positions 1, 2 and 3 storing 13, 25 and 38 again; the window's readout
  and fine steps follow (`UiState::dsp_compat`).
- **The reading of a preset (#13, R4).** `preset::music_controls(…, compat)`: a curve of another
  band count by position (`eq::remap_band_gains_by_position`, `0f05ba5`'s remap, which `3596e99`'s
  application used), on a pick and on the window's band count change alike; twenty bands on the
  Windows ladder (`eq::band_table_in`, `preset::ladder_in`, `MusicLevels::ladder`), a curve on the
  half-octave ladder moved onto it band for band (`fxsound_core::eq::move_to_the_twenty_band_ladder_of`).
- **The level changing (A12).** `App::read_music_controls_in` reads an unedited preset again
  from its file, as a pick at the new level would (as a band count change does, #45), and
  carries edited controls over: every effect keeps the value it plays, and a twenty-band curve
  moves between the two ladders band for band. Nothing is marked or saved. A twenty-band preset
  taken to Interface and sound and back is the preset it was, bit for bit; saved there it is on
  the Windows ladder, and read at Off it is on the half-octave one with every gain where it was
  saved (the application's tests).
- **The export (R6, roadmap §14 #56).** `EndBands::AsTheyAre`: from Interface and sound on the
  Export window offers "Keep the end bands where they are" and `--export-unshifted` sets the same
  choice (`export_unshifted`); unshifted, a centre is limited only to the equalizer's
  10 Hz–21 kHz. Shifted stays the default and the only export below that level.
