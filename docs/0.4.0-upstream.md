# FxSound for Linux 0.4.0 — additions from the upstream review

The user approved all nineteen recommendations of the review of the Windows FxSound
(github fxsound2/fxsound-app up to 1.2.16.0, cloned at `~/Загрузки/fxsound-app`), with the
critic's corrections. The full review, in Russian, with every commit/issue/file citation, is
`~/Загрузки/fxsound-upstream-review.md` — read its §2 table row for the item you implement,
and its §10.1 corrections. This file is the contract; the review is the evidence.

Upstream is a native Windows program; nothing here is ported as code except the C DSP logic
(U1–U3). Everything else is re-done with PipeWire / WirePlumber / D-Bus / egui.

Where each item lands: **engine** = `crates/fxsound-audio` (+ `fxsound-core` messages/settings,
+ `fxsound-dsp` for U3), done in the main checkout after Phase B; **app** = `crates/fxsound-app`,
`crates/fxsound-ui`, `crates/fxsound-preset`, packaging, done in Phase C part 2.

## New `fxsound-core` API (added once, by the first engine item; the app uses it after merging)

```rust
// messages.rs
UiToAudio::SetDevicePriority { direction: DeviceDirection, names: Vec<String>, new_devices_first: bool }  // ranked node.names, first = most preferred; empty = follow the system (rule 6, issue #629)
                                                      // new_devices_first = settings.prioritize_new_output: an unranked device goes before (true) or after (false) every ranked one (BU8)
UiToAudio::SeedTargetVolumes(Vec<TargetVolume>)       // from settings at start-up
UiToAudio::SystemSleeping(bool)                       // logind PrepareForSleep: true = about to sleep, false = resumed
UiToAudio::KeepInputAwake(bool)                       // calibration and the microphone meters hold the microphone open (U9, U19)
AudioToUi::TargetVolume(TargetVolume)                 // our virtual node's volume while attached to this target changed; persist it
AudioToUi::Warning { direction: Option<DeviceDirection>, message: String }  // translated text, e.g. one BT device on both lanes

#[derive(Clone, Debug, PartialEq, Serialize, Deserialize)]
#[serde(default)]
pub struct TargetVolume { pub direction: DeviceDirection, pub target: String, pub port: String, pub channel_volumes: Vec<f32>, pub mute: bool }
// port: the card's active route for the node (`analog-output-headphones`), "" when none; not written when empty (BU8)

// DspParams and InputDspParams: pub mute: bool   // the app's own mute; sanitise keeps it. The engine silences a lane itself while the system sleeps (U13)
// settings.rs
pub device_volumes: Vec<TargetVolume>,                // per real target, per direction
pub follow_system_default: bool,                      // default false; true = ignore the priority list (U4, #629)

// fxsound-audio lib.rs (BU8)
pub struct DevicePriority { pub names: Vec<String>, pub new_devices_first: bool }  // as SetDevicePriority carries it
StartOptions { .., pub output_priority: DevicePriority, pub input_priority: DevicePriority }
```

**BU8 amendments (2026-09-23).** The review of the engine work (BU8) changed three parts of this
API after it was first added; Phase C part 2 builds against the block above as amended:

- `SetDevicePriority` carries `new_devices_first: bool` (defect 3). The engine runs a lane's
  rules on a device's arrival in the same tick it lists the device to the app, before the app's
  re-ranked list can reach it, and a device already seen is no newcomer once that list comes: so
  "Prioritize new output devices" could never move the lane. With the flag the engine ranks a
  device the list does not name yet before every ranked one (`true`) or after every one
  (`false`) on that first run. The app sends `settings.prioritize_new_output` with every
  ranking of either lane (U4 files new devices of both directions by it), and sends the
  ranking again when the setting changes; an empty `names` (follow the system) still means no
  ranking, whatever the flag.
- `StartOptions::output_priority` / `input_priority: DevicePriority { names, new_devices_first }`
  (defect 6). A ranking sent as a message after start may arrive after the lane's first pair is
  built, and the Windows rules would have chosen the session default for it, which the ranking
  then had to take the lane away from. Handed over at start, the first choice is the ranking's.
  The app fills them from `device_configs` and `prioritize_new_output` (empty `names` while
  `follow_system_default` is on), and still sends `SetDevicePriority` whenever either changes.
- `TargetVolume::port: String` (defect 7): the name of the card's active route for the node
  (`SPA_PARAM_Route`), empty for a device whose card names none. On a card that is not UCM the
  speakers and the headphones are two ports of one sink, and plugging headphones in only moves
  the route, so a volume kept per `node.name` alone was the speakers' level on the headphones
  (upstream #615 again). An entry is now one per direction, target *and* port
  (`TargetVolume::is_for`, `same_place`), and `Settings::device_volumes` keeps one per port. The
  field defaults (`#[serde(default)]`), so files written before it read as `port = ""`, and it is
  left out of the file when empty. `Settings::remember_target_volume` and
  `Settings::target_volume(direction, target, port)` already key on it; the app keeps the
  `AudioToUi::TargetVolume` it is sent whole, port and all, and never matches on `target` alone.

## Items

- **U1 (dsp+app, S)** Changing the band count remaps the curve instead of zeroing it:
  `fxsound_dsp::eq::remap_band_gains(old: &[f32], new_count) -> Vec<f32>` line-for-line from
  upstream `GraphicEqSet.cpp:200-245` (182a329): shrinking picks the nearest band
  `1 + (int)((i-1)*(old-1)/(new-1) + 0.5)`, growing interpolates linearly, old == 1 copies.
  `App::set_band_count` and `--num_bands` use it. `App::restore_defaults` resets the count to 10
  through it and keeps the curve.
  **Amended by the 0.4.0 audit (#13):** the remap works by frequency, not by position. When a
  count goes up, the curve is read linearly in log-frequency and held past its ends. When it
  comes down, a curve read from the smaller ladder comes back exactly if the larger ladder
  reaches as far at both ends and has a band on or between every two neighbouring bands of the
  smaller one, which every pair of the window's counts (5/10/15/20/31) does. Any other curve is
  read the same way, held past its ends, and never leaves its own range. So 10 → 31 → 10
  restores the curve, 14 → 15 → 14 does not, and a 62.5 Hz boost stays at 63 Hz on 31 bands
  instead of moving to 20 Hz. `docs/spec/09-dsp-eq.md` §14 has the details. The signature is
  unchanged.
  **Amended again (audit #13, held ends):** past the old curve's ends the gain is no longer held
  but tapers to 0 dB over one old band spacing, because the held bands added up to a sub-bass
  shelf (+12.8 dB at 25 Hz for a ten-band +6 dB at 62.5 Hz on thirty-one bands, where ten bands
  play +0.5 dB); the round trips between the window's counts stay exact, and "never leaves its
  own range" now includes 0 dB. A shrink that cannot be exact lets the new end bands take a
  boost that lies past them, tapered, so a sub-bass boost is not dropped. And
  `remap_band_gains` reads gains as if on the standard ladder of their count: for a curve on
  other centres (a Windows twenty-band curve, a dragged band) `App::set_band_count`, `--num_bands`
  and the settings restore path must pass the live centres, through
  `fxsound_dsp::eq::remap_curve(live_centres, live_gains, new_count)`.
- **U2 (dsp+app, S)** A preset lands on the user's band count: if `preset.eq_bands.len() !=
  num_bands`, keep the live frequency ladder and interpolate the preset's gains onto it
  (upstream `DfxDspEq.cpp:127-247`); copy frequencies only when counts match; an empty EQ in a
  preset means EQ on and flat.
  **Amended by the 0.4.0 audit (#13):** `fit_preset_gains` reads the preset's gains at the live
  centres, using the preset's own centres (see U1). Only equal counts copy.
- **U3 (dsp, S)** EQ off disables the whole GraphicEq block: master gain, balance and the
  volume leveller (upstream aad64c1, `dfxpProcessReal.cpp:143-170`). Power off: only master
  gain, without balance, and only when EQ is on (`SosProcess.cpp:500-516`). Fix the tests that
  assert the old behaviour and the README chain diagram.
  **Amended by the 0.4.0 audit (R3, option b, chosen by the user):** power off applies the
  master gain *and* the balance, by side on surround as well. It does so behind the same EQ test
  as the powered path, which is unchanged: EQ off still takes master gain, balance and levelling
  out while the power is on, as the audit's "keep" list asks. So the bypass is the powered gain
  stage and nothing else, and switching FxSound off moves neither the level (beyond Dynamic
  Boost's 0.3 dB ceiling) nor the balance, whether the EQ is on or off. The half of (b) that
  said "whether the EQ is on or off" is not taken, and **needs the user's confirmation**: with
  the EQ off it would bring in, on switching off, a master gain and a balance the powered path
  does not play (at master gain −6 dB and balance +6 dB, −0.3/−0.3 dB powered against
  −12/−6 dB off, a step of 11.7/5.7 dB), which defeats the reason (b) was chosen ("no volume
  jump"). The only other way to have both, running the gain stage while powered with the EQ
  off, would undo the block above, which predates aad64c1 (before it the EQ-off branch ran the
  levelling alone) and which the audit keeps. What remains of the original's EQ dependency is
  the one the powered path has too. `crates/fxsound-dsp/src/engine.rs` pins it in
  `switching_fxsound_off_with_the_equalizer_off_does_not_move_the_level` and
  `the_power_switch_moves_neither_side_by_more_than_dynamic_boosts_ceiling`.
  The balance also acts by side on surround layouts (audit #44).
  **Amended by the 0.4.0 audit (#11):** the EQ switch fades the block in or out over 20 ms,
  mixing its output with its input, instead of switching it between two samples; what is in the
  block, and what the bypass keeps, is unchanged. The power switch still acts at once.
- **U4 (engine L + app)** The device priority list chooses the device. App: every real device
  seen in `AudioToUi::Devices` is added to `device_configs` of its direction (front when
  `prioritize_new_output`, else back); the ordered list goes to the engine with
  `SetDevicePriority`; combos, tray and `--next-output/--next-input` sort by rank; a Settings
  toggle "Follow the system's default device" (`follow_system_default`). Engine: in
  `choose_device` a new device wins only if ranked above the current one; when the current one
  goes, the first *available* ranked device is taken; unranked devices come last. **Available**
  = node present AND its Device's `SPA_PARAM_Route` for that node is not `available=no`
  (subscribe to Route on Device globals; match by `card.profile.device` / `device.id`);
  an unavailable node never wins, including rule 7's `real[0]`, while any node of its direction
  is available. The one exception: when nothing of that direction can be heard (a desktop whose
  only output is a sleeping monitor, a headset jack that is the only microphone and is empty),
  the rules, ranked or not, run on the nodes that are present rather than end in
  `NoOutputDevices`/`NoInputDevices`, which would tear down `fxsound_sink`/`fxsound_source`,
  drop the lane's claim on the default and move every stream off it until the port wakes; a pair
  left on the silent port simply plays again (`devices::candidates`). Needs a `pw-dump` fixture
  of a UCM card with dead HDMI routes. Same for the input lane.
- **U5 (engine, S)** Rule 5 (a device just appeared) must not depend on the device count
  growing: take the first real device whose name is not in `previous_names` (PR #532).
- **U6 (app, S)** A device preset applies immediately when set in Settings for the current
  device, and after deleting or resetting presets the current device's preset is selected
  (83ccf5e, 7f160b6). A target change not initiated by the GUI (`AudioToUi::Attached`) also
  applies that device's preset.
- **U7 (engine, S)** Mono outputs are accepted (Bluetooth HFP, mono USB headsets): the refusal
  was a Windows-driver workaround (`sndDevices.h:32-39`). `is_refused_mono()` false for outputs;
  NODE 1 stays stereo, the NODE 2 adapter downmixes. Test with a 1-channel
  `bluez_output.*` headset-head-unit fixture.
- **U8 (engine, M)** Bluetooth A2DP↔HFP switches and short drop-outs do not move the output to
  the speakers: `node.dont-reconnect = true` and `node.dont-fallback = true` on both lanes'
  device-facing streams **and** `node.linger = true`; the `already` check compares the target's
  `object.serial` (or global id), not only its node.name, so a sink that comes back under the
  same name is re-linked (WirePlumber 0.5.17 `linking/prepare-link.lua:71-75` never re-links a
  handled dont-reconnect stream); when a target disappears but its Device (`device.id` /
  `api.bluez5.address`) is still present, defer the lane's rules ~2.5 s. graph_churn test:
  remove a sink and re-add it with the same node.name within 500 ms → no rebuild to another
  device, and NODE 2 is linked again afterwards. As built (BU8, `docs/spec/12-audio-io.md` §22):
  the wait also ends on the next tick when the card adds a node of the lane's direction under a
  name it did not have when the node went (an ALSA profile that renames its sink; "had" counts
  the card's nodes that went just before the lane's, since ACP removes and re-adds a card's nodes
  one at a time in device order); every node that goes while its card stays counts as seen by
  its direction's rules until `RETURN_WAIT` is up, whichever lane was on it, so back under its
  name it takes no lane as a new device; and a `SelectDevice` naming the picked device within
  `RETURN_WAIT` of its return is not a fresh pick. A card switched to its `off` profile still
  holds the lane silent for the full 2.5 s.
- **U9 (engine+app, M)** WirePlumber 0.5's Bluetooth microphone is a loopback node
  (`bluez_input.<addr>`, `bluez5.loopback = true`, no `api.bluez5.*`): recognise it (and a
  Device with `device.api = bluez5`) as a headset; `native_rate` from `api.bluez5.codec`
  (cvsd 8 kHz, msbc 16 kHz, lc3_swb 32 kHz), default 16 kHz; skip `api.bluez5.internal = true`
  nodes. When one Bluetooth device is the target of both lanes, send `AudioToUi::Warning`
  ("Using this headset's microphone switches it to call quality: music plays in mono at 16 kHz").
  App: calibration opens a short capture of `fxsound_source` without a link-group so
  WirePlumber enables HFP before measuring; the microphone picker explains that a Bluetooth
  microphone wakes when an application records from FxSound (Input).
- **U10 (engine+app, M)** FxSound's volume is per target device: `state.restore-props = false`
  on `fxsound_sink` and `fxsound_source` (WirePlumber otherwise restores one volume for every
  target); the engine reads `channelVolumes`/`mute` from NODE 1's Props in `param_changed`,
  reports them as `AudioToUi::TargetVolume` (the app persists `device_volumes`), and after
  building a pair applies the remembered volume of the new target to its own NODE 1 with
  `set_param(Props)`; an unknown target gets `min(current, remembered default)` — never raise.
  A 20–50 ms linear ramp from silence on the first blocks of a new pair (RT-safe, in the lane
  DSP). Never write Props of the real device.
- **U11 (engine, M, measure first)** On a PRIVATE PipeWire: does NODE 1's adapter apply the
  sink volume before `process()`? (pink noise, VL=4, sink at −20 dB, compare the drop at
  NODE 2.) If yes, keep the adapter's soft volume at unity and apply `channelVolumes`/`mute`
  after the chain; the published Props do not change. If not confirmed, record the measurement
  in `docs/spec/12-audio-io.md` and change nothing.
- **U12 (app, S)** Power off hands the system default back (`SetAsDefault { want: false }` for
  both lanes); power on takes it again. While off, the window shows the system default as the
  selected device. Document in README "Deliberate differences" that bypass-only is gone.
- **U13 (app+engine, S)** Sleep: the app listens to logind `PrepareForSleep` on the system bus
  (zbus); `true` → `SystemSleeping(true)` → both lanes mute; `false` →
  `ResetFilterState` on both lanes, rules re-run with the U8 deferral, then unmute. No sleep
  inhibitor (upstream PR #533 decision). As built: the engine mutes each lane itself, after its
  chain, through an override its NODE 1 reads beside the snapshot's `mute` (the app does not set
  `mute` for this); no device rules run while asleep; on waking, a lane whose device is not back
  waits up to `RETURN_WAIT` (2.5 s) for it whether or not its card is there, and each lane is
  unmuted on the tick its rules leave it attached, or after 2 s. A sleep with no wake is given up
  after 60 s of the system being awake.
- **U14 (app, S)** `--status --json` is a superset of upstream `printStatus`
  (`FxController.cpp:609-683`): `presets.built_in[]/user_defined[]` with `{name, modified}`,
  `selected_preset`, `output_devices[]/input_devices[]` (node_name, description, present),
  `selected_output/selected_input`, `equalizer{num_bands, master_gain, volume_leveling,
  filter_q, balance, bands[{index, frequency, gain, min_frequency, max_frequency}]}`, effects
  under upstream's keys without rounding, a `schema` number. Keep our own keys. As built: the
  objects cannot go under upstream's key and keep the superset — `fxmcp`'s `status.go` decodes
  `output_devices` as `[]string` — so `output_devices[]/input_devices[]` are upstream's array of
  description strings (the devices present, in priority order), and the (node_name, description,
  present) objects are `output_device_list[]/input_device_list[]`, which `ListDevices` answers
  with.
- **U15 (app, S)** Preset commands from the CLI, socket and D-Bus refuse where the menu refuses

- **U16 (preset, S)** Export writes the saved preset file, not the AutoSave copy (PR #155):

- **U17 (app, S)** Bulgarian: extract `FxSound_bg_txt` from upstream v1.2.16.0

- **U18 (ui+app, M)** Face B of the effects column: the flip button (assets exist) shows the
  original's second face — band count, master gain, volume leveling, filter Q, balance,
  Restore Defaults (upstream `FxAudioControls.cpp`, f58a423) — with upstream semantics
  (Restore Defaults keeps the curve, U1). Check the spec `docs/spec/03-controls.md` for its
  geometry; the equalizer's `with_controls` path exists but is never called. As built:
  `fxsound-ui/src/views/equalizer_controls.rs`, at §5.1's rectangles; the flip at (145, 5) is on
  the card, which now also gets `FxAudioControls::paint`'s `ControlBackground` fill (§5.8), and
  turns `ViewScratch::column_face` over — the window's, not a setting, as upstream's
  `effects_shown_` is. `with_controls` and the EQ bypass switch drawn only through it are retired:
  face B is the one place these controls live. With the power off the whole card, the flip
  included, is disabled; readouts stay at a disabled label's half alpha. While the EQ is off
  (U3) the sliders whose stage goes with it are drawn grey and stay live. A right-click resets a
  level without first dragging it to the pointer (`FxAudioSlider::mouseDown` keeps the right
  button from `Slider`). On a microphone face B shows what the voice chain has: the band count,
  **Makeup Gain** in Master Gain's row (the same `SetMasterGain`, which on a voice is the preset's
  makeup; 1 dB steps, since voice presets are voiced at 3, 5, 7 and 9 dB), Filter Q in the next
  row, and Restore Defaults where it always is; Volume Leveling and Balance are not drawn.
- **U19 (engine, S)** The input lane's capture stream (`fxsound_capture`, device-facing) gets
  `node.passive = true`, so the microphone is not held open when nobody records from
  FxSound (Input). Verify on a private graph that a recorder linking to `fxsound_source` starts
  the capture; if it does not (link-group driver grouping), fall back to the output lane's
  B5 pattern: `set_active(false)` on the capture stream while `fxsound_source` is Paused. Keep
  it non-passive while calibration or the microphone meters need it. As built: verified on
  PipeWire 1.6.8 — a `pw-record` linked to `fxsound_source` runs the source, the capture stream
  and the microphone, and gets the processed microphone; unlinked, all three go idle — so the
  passive capture stream shipped and the fallback did not (on a server older than 0.3.68 the
  capture stream stays non-passive, as before). `KeepInputAwake(true)` makes the engine record
  `fxsound_source` itself with a stream of its own, `fxsound_mic_check`: no link-group, not
  passive, `target.object = fxsound_source`. It runs the pair and the microphone like any
  recorder, and it is what WirePlumber 0.5's `autoswitch-bluetooth-profile.lua` switches a
  Bluetooth headset to its call profile for — a stream with no link-group that reaches the
  headset's loopback microphone, followed through `fxsound_source`'s group — so U9's
  calibration capture is this message, not a stream of the app's.

- **Side findings (app, S)** remove the upstream survey/what's-new URLs from `notify.rs`;
