# Checking whether a preset is voiced correctly

Two answers to a question that has no single one, designed 2026-09-20. Tracker items `s5-09`
(the measurable half) and `s5-10` (the half no measurement replaces).

The twelve genre presets are provably **distinct** from one another — measured on a third-octave
grid through the real engine, by `crates/fxsound-dsp/tests/shipped_presets.rs`. What is not
established, and cannot be by that test, is whether the one called Jazz sounds like jazz.


## Objective measurement of genre-preset voicing: what can actually be measured through the real engine, what reference data exists as numbers, which corpora are licence-clean for this AGPL repo, and where the measurable ends

Build it in three layers, cheapest first.

**Layer 1 — an analysis module in the workspace, no new runtime deps, no downloads.** Add `ltas_thirds()` (Welch, Hann, 50% overlap, 8192-point realfft, power summed into the 29 third-octave centres already tabulated in `crates/fxsound-dsp/tests/shipped_presets.rs:167`), `lufs_integrated()` (BS.1770-4: K-weighting as two biquads on top of the existing `crates/fxsound-dsp/src/biquad.rs`, 400 ms blocks at 75% overlap, −70 LUFS absolute gate, −10 LU relative gate), `true_peak_dbtp()` (4× oversample), and PLR = true peak − integrated LUFS. Everything else in this proposal is built out of those four.

**Layer 2 — the falsifiable test, offline and in CI.** Check in `assets/reference/ltas-<genre>.csv`: 12 genres × 29 third-octave values, level-normalised to shapes, derived in Layer 3 and carrying a provenance header. Generate deterministic seeded program material per genre (pink noise shaped to that genre's reference, plus a noise-burst train at a genre-typical crest factor so the dynamics stages actually engage), render all 12 presets across all 12 materials through the real `Engine`, loudness-match output to input, and compute ΔD(P,g) = D(out,R_g) − D(in,R_g) where D is the weighted RMS dB error between level-normalised shapes over 40 Hz–16 kHz.

The test asserts one thing: **for each genre column, the preset whose ΔD is lowest is the preset of that name**, and it reports the margin over the runner-up. That claim is relative, so it holds up even when the reference curve is only approximately right — which it will be. Report, don't assert: ΔLUFS, ΔPLR, spectral centroid shift, clipped-sample count, and the spread of ΔD across materials. The whole matrix runs in seconds.

This is strictly stronger than what `shipped_presets.rs` can do today, because it sees Dynamic Boost's auto-gain and its −0.3 dBFS ceiling, the leveller, Bass, Ambience and Surround — none of which an impulse through `GraphicEq` ever touches, and none of which are bypassable.

**Layer 3 — the reference curves, derived once, offline.** There is no per-genre reference spectrum available as numbers anywhere: Pestana/Reiss is figures behind the AES paywall, iZotope's and Har-Bal's are proprietary and embedded, and the Million Song Dataset's 12 Echo Nest timbre coefficients are not invertible to a dB spectrum. So derive one. Primary: AcousticBrainz's `lowlevel.barkbands.mean` (27 Bark-band energies per track), CC0, ~29.5M tracks, 1 GB zstd, joined to genre and release year by MBID through MusicBrainz's own CC0 genre data — commercial masters, the material the presets were actually voiced against, under a licence this AGPL repo can vendor outright. Cross-check against a second reference derived by rendering licence-filtered FMA audio (metadata CC BY 4.0, per-track `license` column, decode via an external ffmpeg pipe so `fxsound-dsp` keeps its single dependency). Sanity-check both against the one public number in the literature: roughly −5 dB/octave from 100 Hz to 4 kHz.

**And Layer 0, which is the smallest and probably the most useful: the blind A/B harness.** I cannot hear the presets, and nothing above changes that. What I can do is remove the two things that make informal listening lie — render loudness-matched pairs at identical integrated LUFS, in randomised order, with a hidden key — and score the user's answers with a binomial test. Twelve presets, ten trials each, is an evening's work for a person who can hear, and it is the only step in this entire proposal that measures sound rather than a proxy for sound.

Build order: Layer 0 and Layer 1 first (both small, both immediately useful), then Layer 3's AcousticBrainz extraction, then Layer 2's test once there are curves to test against.

### Approaches considered

- **Analytic EQ response only (what ships today)** — *viable, trivial*. Keep it. It answers 'are these twelve different from each other' and it answers it well. It cannot answer 'is Jazz jazz', and no extension of an impulse test can, because the stages that colour the result are nonlinear.
  - Costs: Nothing — it is the current baseline. But it measures the EQ block alone. It never sees Dynamic Boost's auto-gain and −0.3 dBFS ceiling, the leveller, Bass, Ambience or Surround, all of which are program-dependent and none of which are bypassable. So what it measures is not what a listener gets.
- **Genre-shaped synthetic program material through the FULL engine, scored as a 12×12 confusion matrix** — *recommend, medium*. This is the one that can be built and run today, entirely offline, in CI, in seconds, with no download and no licence question. And it is a genuinely stronger claim than the current tests: it exercises the whole nonlinear chain, and it is *relative*, so it survives the reference curve being only approximately right. Stationary noise under-exercises the transient behaviour — that is what the burst train is for, and it is still weaker than real music.
  - Costs: Nothing in the compatibility contract — no .fac file changes, no engine changes. It adds one data asset (12 × 29 floats) that must be regenerated if the reference method changes, and a test whose failure means 'this preset is not the best fit for its own genre', which will be uncomfortable the first time it runs.
- **Render a real genre-labelled corpus (FMA) and measure the same ΔD over thousands of tracks** — *viable, large*. The honest version of the test, and the only one where the material is real music. Run it once offline, check in the numbers, do not put it in CI. Note the coverage gaps up front: Metal and Trap are thin subgenres under Rock and Hip-Hop in FMA's 161-genre tree, and 70's / 80's are not genres at all — FMA has no era coverage, so those two presets are simply not testable by rendering.
  - Costs: Nothing in the repo. Costs 22–93 GiB of download and hours of render. Never redistribute audio or renders — only derived numbers, with FMA's CC BY 4.0 attribution recorded. Coverage is the real break: FMA is indie/amateur CC material, not commercial masters, so it was mastered by different conventions than the Windows presets were voiced against.
- **Build the per-genre reference curves from AcousticBrainz barkbands (CC0, commercial masters)** — *recommend, medium*. This is the answer to 'which genre reference spectra exist as numbers': none do, so make one. This is the only route to a reference built from *commercial* masters — the material the presets were actually voiced against — under a licence (CC0) that an AGPL repo can vendor without conditions. 27 Bark bands is coarser than 29 third-octaves and the resample is an approximation; say so in the asset header.
  - Costs: Nothing. Two accuracy caveats that must be written down beside the numbers: the analyses were run by users on their own files of unknown encoding quality, and MusicExtractor applies replay gain, so absolute level is not comparable across tracks — which is exactly why every comparison in this proposal is shape-only and loudness-matched.
- **Vendor a published or commercial reference curve (Pestana/Reiss, Ozone Tonal Balance, Har-Bal)** — *reject, small*. There is exactly one usable number in this whole literature that is public: the ≈ −5 dB/octave decay from 100 Hz to 4 kHz, and it is a global curve across all popular music, not a per-genre one. Use it as a sanity check on a self-derived reference (does the derived curve slope roughly −5 dB/oct through the midband?) and nothing more.
  - Costs: Licence, and accuracy. The AES per-genre curves exist only as plots behind a paywall; digitising a plot into a repo asset is both a rights problem and a precision problem. iZotope's 30+ curves and Har-Bal's are in-house, undocumented and embedded in proprietary plugins — extracting them into an AGPL-3.0 repo is not defensible.
- **Psychoacoustic proxies for the words that have no spectrum (sharpness, roughness, pumping, image width)** — *viable, medium*. Worth doing for the ceiling cases, and worth being blunt about what it buys. Sharpness in acum is a standardised measure of a signal property that correlates with the word 'bright' on stationary content. It is not a measure of whether a cymbal sounds harsh in a mix. Report the number, never let it decide.
  - Costs: Nothing in the repo — these run on rendered output, offline. Implementing ISO 532-1 natively in Rust would be a large lift for little gain; call MoSQITo from a script instead.
- **Blind A/B harness — I cannot hear, but I can make the user's listening cheap and unbiased** — *recommend, small*. This is the direct answer to 'is there a way for you to listen': no, there is not, and there is no proxy that closes the gap. But loudness-matching and order-randomisation are exactly where informal listening goes wrong — a preset that is 2 dB louder wins every sighted comparison — and those are mechanical, so I can do them. Highest value per hour of anything in this list.

### Notes

**What `process_wav.rs` can do today, and what it is missing.** It reads 16-bit PCM WAV only (it walks the chunk list properly, so real files with LIST/fact chunks work), applies a `.fac` preset or individual effect flags on the GUI's 0..10 scale, runs the real `Engine` in 1024-frame blocks exactly as an audio callback would, prints peak L/R from `engine.meters()` and a count of samples that exceeded full scale, and writes the result back. To render a corpus it needs: MP3/24-bit/float input (or an external ffmpeg pipe — cleaner, keeps `fxsound-dsp`'s single dependency intact), a bypass A/B render in one pass, LUFS and true-peak measurement, third-octave LTAS output, loudness-matching, and batch mode over a file list. None of that requires touching the engine.

**Three honest limits, stated plainly.**

*First, matching a genre reference proves 'not wrong', never 'right'.* A preset that lands exactly on the genre mean is average, and average is not what a preset is for — a preset is a deliberate colour. The strongest true statement this method can ever produce is: "the Jazz preset moves jazz-labelled material toward the jazz reference more than the other eleven presets do, by a margin of X dB with a CI of Y." That is a real claim and it is worth having. It is not "Jazz sounds like jazz".

*Second, the between-genre signal may be small and partly the wrong signal.* Elowsson & Friberg (AES 142, 2017) found that LTAS variation between genres is mainly a side-effect of percussive prominence. So a per-genre LTAS reference partly encodes "how much drums this genre has", not "how this genre should be EQ'd", and the between-genre spread is likely small against the within-genre spread. If the confusion matrix's diagonal margin falls inside its bootstrap CI, the correct conclusion is "these presets are provably distinct but not demonstrably genre-targeted" — and reporting that is a better outcome than a green test.

*Third, some judgements have no proxy at all.* "Does it sound harsh", "does the vocal sit right", "is that boost musical or resonant", "does the leveller pump", "does Surround widen or hollow it" — none of these are reachable. DIN 45692 sharpness, ECMA-418-2 roughness, EBU R128 LRA and inter-channel correlation each measure a signal property that correlates with one of those words on constrained material. They are worth computing and worth never letting decide anything.

**Repo-specific licence findings** (this repo is AGPL-3.0-or-later, `Cargo.toml:16`): AcousticBrainz data is CC0 — vendor freely. FMA metadata is CC BY 4.0 — vendorable with attribution; FMA audio is per-artist CC with a `license` column to filter on, and must never be redistributed, nor must renders of it. MTG-Jamendo metadata and the AcousticBrainz Genre Dataset are both CC BY-NC-SA 4.0 — usable as local scratch, **not** vendorable into this repo. MUSDB18 and MedleyDB are academic-use-only stems corpora — reject on all three of size, shape and licence. MoSQITo is Apache-2.0 (verified via the GitHub API) and compatible.

**Two presets this cannot reach at all.** "70's" and "80's" are eras, not genres. No open corpus carries era-labelled renderable audio — FMA's release dates are upload dates for contemporary CC material. AcousticBrainz joined to MusicBrainz release years can give era *reference curves* (and era trend is precisely what the Pestana corpus was about), so those two presets can be checked against a curve but never by rendering era-appropriate material. Say so in the report rather than quietly testing them against something else.

**Structural suggestion:** follow the pattern already set by `docs/voice-presets-research.{md,json}` — a machine-readable JSON carrying every source, every derived number and every caveat, with a short human-readable MD beside it. The reference curves themselves belong in `assets/reference/` as CSV with a provenance header naming the dump date, the join, the track count per genre and the licence.

## Listening harness for judging the twelve revoiced genre presets (fxsound-linux)

Build the offline blind shootout; keep the live keybind as an unblinded second pass. Nothing in Rust changes — process_wav already does the whole job, which I confirmed by rendering through it.

WHAT GETS BUILT (three shell files under scripts/voicing/, roughly 120 lines total):

1. render.sh. For each genre: dry = the source excerpt untouched (not an engine render with power=0, and not a flat preset — Dynamic Boost is never bypassed and still imposes its -0.3 dBFS ceiling and at least +0.5 dB once auto-gain engages, so only the untouched file is a true anchor); old = `target/release/examples/process_wav in.wav old.wav --preset <shipped .fac>`; new = the same with the revoiced .fac. Then measure all three with `ffmpeg -i X -filter:a ebur128 -f null -`, take the minimum integrated LUFS (always the dry file), attenuate the other two by the difference with `volume=NdB` — attenuate only, never boost, so nothing clips. Then mux: `ffmpeg -i dry -i a -i b -map 0:a -map 1:a -map 2:a -c:a flac -metadata:s:a:0 title=1 ... <genre>.mkv`, with the three inputs in an order shuffled per genre, and append "genre<TAB>track1=dry<TAB>track2=new<TAB>track3=old" to key.tsv. Verified: render 0.097 s per 30 s per preset, the matched files land on identical LUFS in a single pass (-26.3, -26.3, -26.3), and mpv sees three switchable tracks.

2. session.conf, an mpv --input-conf. a / s / d → `set aid 1` / `2` / `3` (direct, instant, keeps position — verified over IPC: the track changed while time-pos ran on). 1 / 2 / 3 → `run /bin/sh -c 'echo "$genre\t$track" >> votes.tsv'` followed by `playlist-next` (verified: the run binding wrote its file). b / h / t / p append a one-letter flag — boomy, harsh, thin, pumping — to the current line. `--loop-file=inf` so a 45-second excerpt repeats indefinitely while they switch. One mpv invocation with all twelve .mkv files as the playlist; they never touch a terminal during the session.

3. unblind.sh. Joins votes.tsv with key.tsv and writes docs/voicing-verdicts.tsv, one line per preset:
   preset<TAB>winner(new|old|dry)<TAB>flags<TAB>confidence(sure|unsure)
That file is the deliverable an assistant reads and turns into a revision: "winner=dry" means the voicing is a net loss and should be pulled back toward flat; "winner=old" means the revoicing regressed; "flags=p" points straight at Dynamic Boost, which is the one control where the port has a known cliff (positions 6 through 10 are all +11.60 dB, so if pumping is flagged the fix is to move the stored value down into the 0..70 range where it still does something, not to nudge it).

WHAT THE PERSON DOES, AND FOR HOW LONG:
- 10 min, once: drop one track per genre into material/. Their own files first — familiarity beats licensing for a private judgement, and these renders never leave the machine. Their ~/Музыка is empty, so for genres they have nothing for, fetch.sh pulls the pinned free material below. Pick the excerpt from a busy passage, not an intro: `ffmpeg -ss 60 -t 45 -ar 48000 -ac 2 -c:a pcm_s16le`. 48 kHz and 16-bit are required — process_wav reads 16-bit PCM only, and 48 kHz is the only rate PipeWire allows here, so the offline render matches the live path exactly.
- 1 min: `./render.sh` (the DSP part is about 4 seconds for all twelve; the ffmpeg loudness passes dominate).
- 25 to 35 min: `mpv --input-conf=session.conf --playlist=session.m3u`. Per item, the OSD shows one instruction: "Same 45 seconds, three versions, level-matched. a/s/d to switch instantly. Which one do you want to keep listening to — 1, 2 or 3? If the one that sounds untouched is the best of the three, say so. Optional: b boomy, h harsh, t thin, p pumping." About 2.5 minutes each, two keystrokes.
- 0 min: the verdicts file writes itself; `./unblind.sh` prints it.
Total: under an hour, most of it actual listening.

WHY THE QUESTION IS PHRASED THAT WAY: "does Jazz sound like jazz" has no answer. "Of three level-matched renders of the same track, which do you want to keep listening to, and is the untouched one the best of them" has an answer in thirty seconds, and it yields the two facts that can be acted on — a direction of preference, and a floor check that catches a preset which is actively harmful. Blind, because they authored the new voicings; level-matched, because otherwise the answer is just "the loudest one".

MATERIAL, per genre: Classical → Open Goldberg Variations, Kimiko Ishizaka, CC0, 24-bit FLAC (verified via the archive.org metadata API). R&B, Trap, Pop, Modern Rock, Alternative Rock → the blocsonic collection, 425 CC-licensed items of modern-production hip-hop, funk, soul and rock (verified, 425 items). Jazz → Podington Bear (Chad Crouch), CC-BY, on archive.org and FMA. Metal → the archive.org netlabels collection has ~2500 metal-tagged CC items; pin one CC-BY or BY-SA release by identifier. 70's, 80's, Classic Rock, Modern Country → there is essentially no good free material; be honest about it. Those four should be judged on their own records, or accepted as judged against a modern proxy with the caveat written into the verdicts file. Pin every identifier into a material.lock the first time rather than searching per run: I measured that archive.org's subject tags are unreliable — a `subject:"country"` query in the netlabels collection returned field recordings from Crete as its top hit. Prefer CC0 / CC-BY / CC-BY-SA items over the many NC-ND ones, so a render can be attached to a GitHub issue later without a licence problem.

### Approaches considered

- **Offline render + loudness match + blind three-way preference in one mpv window (dry / shipped / revoiced)** — *recommend, small*. It is the only option that removes the two biases that would otherwise make the whole exercise worthless. Measured on one identical input: dry -26.3 LUFS, Metal -23.0, Pop -20.3, Jazz -18.9 — a 7.4 LU spread between presets and 1.9 to 7.4 LU above dry, because Dynamic Boost is never bypassed. Unmatched, the listener is grading loudness and the loudest preset wins every time. And because they authored the new voicings, sighted comparison grades their own intent. Both fixes cost a few lines. The render itself is free (0.097 s per 30 s per preset), so the expensive resource — their attention — is spent only on listening.
  - Costs: Nothing in the shipped code — it adds scripts and one committed verdicts file. The only contract it touches is that render.sh must read the .fac files through fxsound_preset::parse, so it inherits the byte-for-byte round-trip requirement rather than threatening it. It does not exercise the PipeWire path, the output device selection, or preset switching in the running app.
- **Live A/B through the running app on a keybind** — *viable, trivial*. Keep it as the second, unblinded pass — not the instrument of judgement. It catches what offline rendering structurally cannot: the real output chain (HECATE G2000 PRO vs Ryzen analog), clicks or dropouts on preset change, and how a voicing wears over an hour of varied material rather than 45 seconds. Offline catches what live cannot: level matching, blinding, position-preserving switching, repeatability, and renders that can be measured afterwards and correlated with the verdict. Note that offline is not an approximation of live here — PipeWire runs 48 kHz with clock.quantum 1024 and process_wav uses BLOCK = 1024 at the file's rate, so with 48 kHz material the offline path runs the same rate and the same block size, including Dynamic Boost's time-varying auto-gain.
  - Costs: Nothing. But it cannot level-match (the gain difference is the thing being switched), cannot blind (the GUI and the notification name the preset), and the comparison is sequential with a preset-change gap rather than instantaneous at the same bar of music.
- **Blind ABX with an existing tool (Lacinato ABX, foobar2000's comparator, LinABX)** — *reject, small*. ABX establishes discriminability. These presets differ by several dB across whole bands and by up to 7.4 LU — of course they are distinguishable, and proving it costs sixteen trials per pair. The maintainer's question is preference plus a floor check ('is this worse than doing nothing'), which is a shootout protocol, not ABX. Narrow exception worth keeping in the back pocket: when the shipped-preset test flags two presets as the same voicing under different names, ABX on that one pair is exactly the right tool and Lacinato's shootout mode would serve as a drop-in replacement for the mpv script.
  - Costs: Nothing, but it answers a question that is already answered.
- **Pre-filled Markdown/TSV scorecard they edit by hand after listening** — *viable, trivial*. Correct output format, wrong input method. Alt-tabbing to an editor twelve times breaks the listening loop and invites batching all twelve judgements at the end from memory, which is where preference data goes to die. Voting from inside the player with one keystroke produces the same file. Keep the hand-edited file only as the fallback if mpv's `run` binding is unavailable — and keep the column layout either way, since that is what an assistant reads back.
- **Formal multi-listener panel, randomised, repeated trials, statistics** — *reject, large*. One person, one machine, two output devices, and time as the scarce resource. A twelve-item single-listener blind preference test is not statistically strong, and it should not pretend to be — its job is to catch presets that are obviously wrong or obviously worse than no processing, which one attentive listener does reliably. State the weakness in the verdicts file rather than engineering around it.
  - Costs: Nothing technically; it breaks the budget.

### Notes

Four things worth carrying forward.

First, the dry anchor has to be the untouched file. Rendering "FxSound off" through the engine is not the same thing: DspParams has a `power` flag that bypasses, but process_wav does not expose it, and at power=true with a zero knob Dynamic Boost still ceilings at -0.3 dBFS. If a true engine-bypass render is ever wanted, adding `--power 0` to process_wav is a two-line change — but for this harness copying the source is simpler and byte-exact.

Second, the loudness spread is the headline number and it is measured, not estimated: on one identical input, dry -26.3 LUFS, Classical -24.4, Metal -23.0, Pop -20.3, Jazz -18.9. Every preset is louder than dry, and they differ from each other by up to 7.4 LU. Any comparison that skips level matching — including every live A/B — measures Dynamic Boost's gain and nothing else. This is also the single strongest argument that the Dynamic Boost cliff (five of eleven slider positions at +11.60 dB) is audible as more than a number: presets sitting above stored 70 are all shouting at the same volume regardless of what their slider says.

Third, the harness and the existing test suite divide cleanly. shipped_presets.rs answers "is this preset internally coherent" — no inaudible Ambience below 39, no saturated Dynamic Boost, no duplicate voicings, no bands summing past what any of them claims. The listening harness answers "is it any good". Neither substitutes for the other, and the verdicts file should say which presets the test already flags so a subjective "this sounds wrong" can be checked against an objective cause before anything is revoiced by ear.

Fourth, one cheap addition for the second round if the first verdicts are ambiguous: since the renders already exist as files, a preset whose verdict is "unsure" between new and old can go straight into Lacinato's shootout mode, or into an ABX of exactly that pair, without rebuilding anything. The pipeline produces the material both protocols need.

Not built, deliberately: any attempt to score the presets automatically against a spectral target. The port's claim is that presets voiced on Windows sound the same here, and a spectral target would be inventing a reference the original never had.
